The root of a mod's world settings. There is no tab level; categories sit directly here. Handed to [`IGearsModApi.OnWorldSettingsLoaded`](/docs/reference/settings/i-gears-mod-api); also [`IGearsMod.WorldSettings`](/docs/reference/settings/i-gears-mod).

### BindSettingsClass(Type)

```csharp
void BindSettingsClass(Type settingsType);
```

Binds a settings class. A type is bound once; later calls for it do nothing.

Scans `settingsType` for tagged static members carrying a `"Category.Setting"` path. Fields and properties tagged [`SettingAttribute`](/docs/reference/attributes/setting-attribute) are assigned the named setting first, then methods tagged [`SettingOnSelectedChangedAttribute`](/docs/reference/attributes/setting-on-selected-changed-attribute) or [`SettingOnEnabledAttribute`](/docs/reference/attributes/setting-on-enabled-attribute) are subscribed.

A world setting raises no OnValueChanged, because its applied value arrives with the world rather than changing under the player. A method tagged [`SettingOnValueChangedAttribute`](/docs/reference/attributes/setting-on-value-changed-attribute) is therefore bound **invoke-only**: it is never raised, and runs only when `SyncSettingsToClass` calls it — which means it must be written with `includeInSync: true`, or it can never run at all. [`SettingOnAppliedAttribute`](/docs/reference/attributes/setting-on-applied-attribute) has no such fallback and is logged and skipped.

**Call this from `IGearsModApi.InitMod`.** `ModSettings.xml` is read before that callback, so every setting exists by then, and it runs exactly once - whereas `OnWorldSettingsLoaded` fires again on every world load and rejoin. Binding is a one-time wiring job; use `SyncSettingsToClass` in the callback for the part that repeats.

This binds and nothing else. No listener is called, whether or not it asked for `IncludeInSync`. Calling this again with a type already bound does nothing at all, so binding from `OnWorldSettingsLoaded` instead is safe - just harder to follow.

Throws `ArgumentNullException` for `null`.

### SyncSettingsToClass(Type)

```csharp
void SyncSettingsToClass(Type settingsType);
```

Calls the opted-in value listeners on an already-bound class with the values their settings hold now.

Calls every method on `settingsType` tagged [`SettingOnValueChangedAttribute`](/docs/reference/attributes/setting-on-value-changed-attribute) or [`SettingOnSelectedChangedAttribute`](/docs/reference/attributes/setting-on-selected-changed-attribute) **with `includeInSync: true`**, handing each the value its setting holds at that moment, exactly as if the event had fired. Nothing is bound or subscribed, so this is safe to call as often as you like.

This is how a mod picks up a new world's values, and it is the only thing that calls a listener with a value no event delivered. `BindSettingsClass` deliberately calls nothing, so pairing the two runs each listener exactly once per world load. Gears applies a world's values before it fires `OnWorldSettingsLoaded`, so calling this from that callback hands every listener the current world's values, on the first load and on every load after it.

A listener without `IncludeInSync` is skipped — it runs only when its event fires. Throws `ArgumentNullException` for `null`, and logs a type that has never been bound rather than doing anything.

When `OnWorldSettingsLoaded` returns, Gears warns about every bound class that has an `includeInSync` listener and was not passed to this method during that callback. The check runs on every world load, so a load that skips the sync is reported even when an earlier one did it. A class with no `includeInSync` listener is never reported.
