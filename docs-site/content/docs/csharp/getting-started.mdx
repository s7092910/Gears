Everything a C# mod needs to talk to Gears: the assembly to reference, the one interface to
implement, when each callback fires, and how to reach your settings without a callback.

## Referencing GearsAPI.dll

Gears ships `GearsAPI.dll` inside its own mod folder. Add a reference to that file from your mod
project. Whether you also ship a copy of it depends on whether Gears is optional for your users:

| Your mod | Copy Local | Result |
|---|---|---|
| **requires** Gears | false | Gears loads the assembly; your mod folder carries no second copy. |
| treats Gears as **optional** | **true** | `GearsAPI.dll` sits in your own mod folder, so the types still resolve for a player who does not have Gears installed. |

<Callout type="warn" title="Optional means shipping the DLL">
  If you want your mod to work for players without Gears, `GearsAPI.dll` must be present in **your**
  mod's folder. Without Gears installed nothing else provides the assembly, and the runtime needs it
  to be loadable the moment it compiles any method that mentions a GearsAPI type.
</Callout>

If your mod is built against one GearsAPI version and the player runs a different one, the
mismatch shows up as a `TypeLoadException` inside your callback. Gears catches it and logs:

```text
[Gears] [GearsMod] '<Your Mod>' is using an outdated GearsAPI: it was built against v2.0.1.0 but Gears is running v3.0.0.0, so '<type>' could not be loaded. The mod needs rebuilding against the current GearsAPI.
```

Rebuild against the current `GearsAPI.dll` when you see it.

## Keeping Gears optional

Nothing in Gears requires your mod to hard-depend on it. Gears finds your `IGearsModApi` class
by scanning; if Gears is absent, nothing scans and nothing is called.

Two things make that work. The first is shipping `GearsAPI.dll` in your own mod folder, as above.
The second is the .NET runtime: a method is only compiled when it first runs, and compiling a
method that mentions a GearsAPI type needs `GearsAPI.dll` to be loadable. So keep every line that
touches GearsAPI types inside classes and methods that only run when Gears is present, and gate
the entry to them:

```csharp
public class MyModInit : IModApi
{
    public void InitMod(Mod mod)
    {
        // Your normal startup here. Do not mention GearsAPI types in this class.
        if (ModManager.GetMod("Gears") != null)
        {
            // Safe: this method is only compiled and run when Gears is installed.
            GearsBridge.Announce();
        }
    }
}
```

Your `IGearsModApi` implementation is a separate class that Gears itself instantiates, so it
never runs without Gears.

If instead your mod **requires** Gears, say so in your mod's description and skip the gate.

## The interface

A C# mod talks to Gears through one interface in `GearsAPI.Settings`,
[`IGearsModApi`](/docs/reference/settings/i-gears-mod-api). It has three callbacks — `InitMod`,
`OnGlobalSettingsLoaded` and `OnWorldSettingsLoaded` — fired in the order below.

Gears finds implementations by scanning **every assembly of your mod** for concrete classes that
implement it:

- Abstract classes, interfaces and open generic types are skipped even if they derive from it.
- The class needs a **public parameterless constructor**. Without one it is skipped with a
  warning naming the type.
- Every matching class is instantiated, and every callback is invoked on every instance. One
  class is the normal case; several are allowed.
- A constructor that throws is logged and that class is skipped. An assembly whose types cannot be
  enumerated is logged and skipped.

## Lifecycle

In order:

1. **The game loads mods** and calls each mod's own `IModApi.InitMod`. Gears is not involved yet;
   `GearsSettingsManager.GetMods()` returns an empty list here and `GetGearsMod(...)` returns
   null.
2. **`GameAwake`.** Gears now:
   1. scans all loaded assemblies for `[SettingsSerializationProvider]` classes (custom value
      types, see [C# Custom Value Types](/docs/csharp/custom-value-types));
   2. builds one `IGearsMod` per loaded mod and reads `<Icon>`/`<Banner>` from `ModInfo.xml`;
   3. finds and instantiates every `IGearsModApi`, for all mods;
   4. calls **`InitMod(IGearsMod)`** on each. Your settings tree is still empty here: nothing has
      been read from `ModSettings.xml`. This is the place to create settings from code if you
      want them to exist before the file is read (see [C# Global Settings](/docs/csharp/global-settings));
   5. parses every mod's `ModSettings.xml`, merging into whatever code created;
   6. restores each player-level saved value into the global settings;
   7. calls **`OnGlobalSettingsLoaded(IModGlobalSettings)`** on each mod. Global values are final
      from here on until the player changes them.
3. **World start.** `OnWorldSettingsLoaded(IModWorldSettings)` fires in one of three ways:
   - **Hosting or single player:** when the world starts, after the save's `WorldModSettings.xml`
     has been loaded (or defaults applied for a new save).
   - **Joining a server:** when the server's world settings arrive with the other config files.
   - **Joining a server that sent none:** every world setting is reset to its default, then the
     callback fires.

   It can fire **more than once per session** (leave a world, join another). It is **skipped for a
   mod that has no world settings**.

<Callout>
  If one of your callbacks throws, Gears logs
  `Error thrown in <Callback>() by <YourType> for <Your Mod>` with the exception and carries on:
  your other `IGearsModApi` classes, and every other mod, still get the callback.
</Callout>

## Reaching settings without a callback

[`GearsSettingsManager`](/docs/reference/settings/gears-settings-manager) exposes two static
methods, `GetMods()` and `GetGearsMod(string)`. The mod name is the `<Name>` from `ModInfo.xml`,
including another mod's. Both return empty/null before `GameAwake`, and `GetGearsMod` returns null
for an unknown name.

```csharp
IGearsMod mine = GearsSettingsManager.GetGearsMod("MyMod");
ISliderGlobalSetting<float> hudScale = mine?.GlobalSettings
    .GetTab("General")?.GetCategory("Display")?
    .GetSetting<ISliderGlobalSetting<float>>("HudScale");
```

## `IGearsMod`

[`IGearsMod`](/docs/reference/settings/i-gears-mod) is what Gears knows about one mod: the game's
`Mod` object, the `GlobalSettings` and `WorldSettings` trees (both never null), and the `IconPath`
and `BannerPath` read from `ModInfo.xml`. Alongside those sit the `Has…` probes and
`SaveSettings()`, which writes the player-level saved settings file on demand.

## A complete minimal implementation

```csharp
using GearsAPI.Attributes;
using GearsAPI.Settings;
using GearsAPI.Settings.Global;
using GearsAPI.Settings.World;

public class MyModGears : IGearsModApi
{
    public static float HudScale { get; private set; } = 1f;
    public static bool FeralNights { get; private set; }

    public void InitMod(IGearsMod modInstance)
    {
    }

    public void OnGlobalSettingsLoaded(IModGlobalSettings modSettings)
    {
        modSettings.BindSettingsClass(typeof(Global));

        HudScale = Global.HudScale.SettingValue;
    }

    public void OnWorldSettingsLoaded(IModWorldSettings worldSettings)
    {
        worldSettings.BindSettingsClass(typeof(World));

        FeralNights = World.FeralNights.SettingValue;
    }

    // Global and world members need separate types: each call resolves every path on the type it is
    // given, and the two use different path formats.
    private static class Global
    {
        // [Setting] finds the setting for you and assigns it to the field.
        [Setting("General.Display.HudScale")]
        public static ISliderGlobalSetting<float> HudScale;

        [SettingOnValueChanged("General.Display.HudScale")]
        private static void HudScaleChanged(IValueModSetting<float> setting, float newValue)
        {
            MyModGears.HudScale = newValue;
        }
    }

    private static class World
    {
        [Setting("Zombies.FeralNights")]
        public static ISwitchWorldSetting<bool> FeralNights;
    }
}
```
